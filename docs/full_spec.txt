# Implementation Prompt — You.com Research Console

Build a local, single-page web application for Ubuntu/Debian GNOME that drives the You.com **Research** (Frontier and Exhaustive), **Contents**, and **Answers** APIs and saves every result as Markdown to a user-chosen directory. Two documents govern this build:

- **The supplied You.com API documentation** is the technical contract. Take endpoint paths, parameters, `research_effort` values, background/async fields, upload mechanisms, status values, streaming behavior, and response schemas from it exactly. Where the supplied docs and current official docs differ, favor the most current confirmed contract and note the difference in the README.
- **The UI-First Project Instructions** are the interface contract. Every screen, state name, color, and component described there is the target. This document defines what the application does; that one defines how it looks and feels.

Before writing code, read both, list any requested behavior the documented API cannot support, and proceed with documented behavior for everything else.

## Architecture

- **Frontend:** one HTML page with CSS and JavaScript, using the component and token system from the UI instructions.
- **Backend:** a small local Node.js/Express server in the same project directory. It owns every authenticated You.com call, `.env` management, polling, upload forwarding, filesystem writes, and structured logging. The browser only ever talks to this backend.
- **Storage:**
  - `.env` in the project root holds the API key. The backend creates, updates, and deletes it. It is listed in `.gitignore`.
  - `data/settings.json` holds the output directory and other preferences.
  - `data/state.json` (or an equivalent small store) holds threads, requests, job IDs, received content, saved paths, and log history so paid work survives a restart.
- **State model:** represent every request with named states that match the UI readout words: `DRAFT`, `SUBMITTING`, `SUBMITTED`, `RESEARCHING`, `RECEIVING`, `RECEIVED`, `SAVING`, `SAVED · VERIFIED`, `RECEIVED · SAVE FAILED`, `FAILED`. Sidebar dots, readouts, logs, and notifications all derive from this one model.

## API Key

Settings exposes a masked key field with Save/Replace and Delete. The backend writes the key to `.env`, reports only presence (`KEY SAVED` / `NO KEY`) to the browser, and redacts it from logs, error bodies, and diagnostics. Deletion requires a confirm dialog and removes the key from `.env`.

## Modes

The composer's segmented control offers exactly four modes: **Frontier**, **Exhaustive**, **Contents**, **Answers**. These are the only API surfaces the app exposes.

**Frontier and Exhaustive** submit to the Research API with `research_effort` set to exactly `frontier` or `exhaustive`, with the documented background/asynchronous option always enabled. Each submission is a deliberate user click; the app tracks and retrieves, and the user alone decides when a new paid request happens.

**Answers** uses the documented Answer API. **Contents** uses the documented Contents API, accepts one or more URLs plus whatever inputs the API documents, and requests Markdown wherever the API offers a format choice.

**Streaming:** when the documented endpoint streams, render partial content incrementally in the reader. When it returns a single response, the readout alone updates. Progress shown is progress the API actually reported.

## Research Tracking

After a research submission succeeds, the backend records the job ID and polls on this schedule, measured from successful submission:

| Elapsed | Interval |
|---|---|
| 0 – 3 min | every 30 s |
| 3 – 6 min | every 15 s |
| 6 – 15 min | every 30 s |

A job You.com has accepted can't be stopped from here, so local tracking never pauses and offers no stop or resume control. It runs until You.com reports a terminal status, then the result is received and saved. Closing the window doesn't end it: the server stays up until every in-flight request has been saved or has failed, then exits; it never waits past the failsafe. On restart, persisted threads and job IDs load into the sidebar exactly as they were, and any job still in flight resumes polling automatically on the same schedule. Polling is a free status check; it never starts paid work.

Tracking ends early only when it can't succeed: You.com rejects the key (401/403) or no longer knows the job (404), and the request moves to `FAILED` with that reason. Other poll errors are retried on the schedule. A failsafe at 15 minutes makes one last check; a result that hasn't arrived by then isn't waited for, and the request moves to `FAILED` with the last status You.com reported.

The readout shows live `ELAPSED`, `INTERVAL`, and `NEXT CHECK` values computed from a single scheduling function so the UI and the actual timer agree.

## Content Integrity

You.com's returned content is the artifact. The app locates it and saves it; it does no editing.

- **Research:** save the returned Markdown string byte-for-byte.
- **Answers and Contents:** request Markdown directly whenever the API supports it. When the API returns structured JSON, keep the complete raw JSON with the request record and create the `.md` file by extracting the documented Markdown/content fields exactly as returned, with all citations, source links, headings, tables, code, footnotes, whitespace, and Unicode intact.
- The Rendered tab is a view of the saved string; the Raw tab *is* the saved string. Processing the same response twice yields identical bytes.

## Output Directory and Filenames

Settings holds an editable absolute path validated by the backend with a write check (`WRITABLE` or the OS's actual error text). A missing directory is created when possible. The same directory serves all four modes, with every file written directly into it.

Filenames use local system time at the moment of the successful write:

```
MM-DD:HHMM.SS.md          → 09-28:1947.34.md
MM-DD:HHMM.SS-01.md       → multi-page Contents results, suffixed in response order
```

Colons are valid on the Linux target. Year-level collisions are accepted as out of scope.

## Save, Verify, Notify

Receipt from the API and persistence to disk are separate milestones:

1. Hold the received content in the request record.
2. Write to a temp file in the destination directory, flush, rename to the final name.
3. Confirm the final file exists.
4. Move the request to `SAVED · VERIFIED` and show the full path.
5. Fire the browser notification.

When the API succeeds and the write fails, the request becomes `RECEIVED · SAVE FAILED`: the report stays fully visible, the OS error appears beside it, and **Save Again** rewrites the retained content with a fresh timestamp and no API call.

**Browser notifications** (standard Notifications API) fire for: research saved and verified (the primary case), Answers saved, Contents saved, a request ending in an API error, and content received with a write failure. Each names the thread, mode, and outcome. In-page state carries the same information regardless of permission status.

## Uploads

Show the attachment control only in modes whose documented endpoint accepts files, and forward files with the documented upload mechanism. Acceptance mirrors You.com's documented constraints exactly; where a constraint is determinable client-side, catch it on the chip before submission; otherwise send the file and show You.com's exact rejection on the chip.

## Errors

Surface You.com's actual HTTP status and message (credentials redacted) in the readout and error block, along with operation, timestamp, and job ID. Distinguish submission failure, background job failure, tracking timeout, filesystem failure, and notification failure, each paired with its recovery action as defined in the UI instructions.

## Threads

Threads work like contemporary AI chat clients: one active request per thread, unlimited concurrent threads each tracked independently, and free switching while requests run. Each thread persists its mode, draft input, attachments, request history, received content, saved paths, and errors. The sidebar lists the 20 most recently used threads in LRU order; the 21st simply drops the oldest from the list. Files on disk are untouched by any UI action. Titles derive from the first prompt and are editable. Creating, opening, switching, or dropping a thread triggers no API call.

## Logging

The backend emits structured entries (timestamp, severity, thread, job ID, operation, outcome, safe details) for: startup, settings changes, submissions, job-ID receipt, each poll, API state changes, content receipt, write attempts, verification, notifications, tracking resumed after a restart, tracking timeout, and errors. The frontend renders them in the log drawer with the color mapping from the UI instructions.

## Scope Boundaries

The app is single-user and local. Usage, cost, and billing displays stay with You.com's own dashboard. Local polling observes remote work; every paid call originates from a user click.

## Visual identity (derived from an ROG-style Conky system monitor)

The look is a dark, high-contrast, information-dense Linux desktop monitor rendered as a proper GUI. Use exactly these colors:

```css
:root {
  --bg:        #0D0D0D; /* window background; the monitor ran at ~80% opacity over the desktop */
  --text:      #F2F2F2; /* primary text and all values */
  --label:     #CCCCCC; /* field labels, secondary text */
  --subtle:    #E6E6E6; /* lightly emphasized secondary text */
  --divider:   #2A2A2A; /* charcoal rules, borders, inactive structure */
  --red:       #CC0000; /* ROG red: section headers, rules, brackets, accented labels, numbers */
  --maroon:    #8B0000; /* down / error / failed */
  --teal:      #98D9C2; /* connected / success / verified */
  --blue:      #437FBF; /* secondary section accent; Contents, links, file paths */
}
```

**Frequency, as in the source monitor:**

- Near-black background everywhere, with surfaces differentiated by charcoal rules rather than lighter panels. Where a second surface tone is truly needed, stay within `#121212–#1A1A1A`.
- **Red is the structural voice, used constantly and thinly**: every section header rule, the bracketed title box, mode/section labels, accented metric labels, and highlighted numbers. It appears on nearly every row as line-work and short text, and almost never as a filled area.
- **White (`#F2F2F2`) for every value** and for report body text.
- **Gray (`#CCCCCC`) for every label** that sits left of a value.
- **Blue** marks one secondary domain the way the dock NIC section did: here, that domain is Contents, source links, and saved-file paths.
- **Teal and maroon appear only as state words** ("CONNECTED"/"DOWN" in the monitor → "SAVED · VERIFIED" / "FAILED" here), plus their status dots.

**Signature patterns to reproduce with HTML/CSS:**

- Section headers as red rules with a bracketed, uppercase title inset: `──[ RESEARCH STATUS ]──────────`. Build this with borders and a title span, so it stays crisp at any width.
- A bracketed title block at the top of the app, in the style of `┌─ NETWORK MONITOR ─┐`, holding the app name in Ubuntu Bold.
- Two-column readouts: gray label left, white value right-aligned, monospaced, in fixed-width columns so values line up vertically down the whole panel.
- Semantic colors applied to the value only, with the label staying gray.

**Typography:**

- Interface, controls, thread titles, and rendered report prose: `Ubuntu, system-ui, sans-serif`.
- Readouts, timestamps, paths, URLs, job IDs, logs, raw Markdown, and every status value: `"Ubuntu Mono", "DejaVu Sans Mono", monospace`, at 13px like the monitor.
- Section headers: Ubuntu Bold, 13–15px, uppercase, letter-spacing 0.
- Report body 15–16px with 1.6 line height; UI text 13–14px; metadata and logs 12–13px.

**Geometry:** 1px charcoal borders, 2–4px radii on controls and panels (up to 8px on dialogs), spacing on a 4px grid, flat surfaces, stable component dimensions across state changes.
